# Стенд производительности: dperf ↔ dperf (сценарий 1)

Две машины, прямое соединение, mlx5 200GbE. Машина A — dperf client, машина B — dperf server.
Перебираются 4 подсценария: bond / без bond × VXLAN / без VXLAN. В каждом ищутся максимальная
пропускная способность и минимальное число ядер, на котором она достигается.

| файл | назначение |
|---|---|
| `env.sh` | все параметры стенда: PCI, IP, ядра, план. Один и тот же файл на обеих машинах |
| `build_dperf.sh` | собирает dperf статически на DPDK из f-stack (`f-stack/build/dpdk-build`) |
| `host_tune.sh` | подготовка машины после перезагрузки: hugepages, governor, IRQ, интерфейсы mlx5 |
| `s1_dperf.sh` | сценарий 1: `server` на машине B, `client` на машине A |
| `parse_dperf.py` | парсер логов dperf: таблицы, оптимум по ядрам, CSV |

Ожидаемая раскладка (как у вас):

```
<каталог>/f-stack/perf-tests/      эти файлы
<каталог>/f-stack/build/dpdk-build собранный DPDK (meson build-каталог или install-prefix)
<каталог>/dperf/                   исходники dperf (проверено на v1.9.0)
```

Пути переопределяются переменными `FSTACK_DIR`, `DPDK_BUILD`, `DPERF_DIR`, `DPERF`, `RESULTS`.

## Подготовка (один раз)

1. **BIOS и параметры ядра** на обеих машинах:
   - BIOS: профиль Performance, C-states выключены, турбо — в одном и том же положении на обеих машинах;
   - grub: `iommu=pt` (`intel_iommu=on` или `amd_iommu=on`), изоляция DPDK-ядер
     `isolcpus=<ядра> nohz_full=<ядра> rcu_nocbs=<ядра>`, затем перезагрузка;
   - HT: в списки ядер `env.sh` берите по одному потоку на физическое ядро.
2. **Сборка dperf** на обеих машинах: `./build_dperf.sh`. Скрипт сам найдёт `libdpdk.pc`
   в `f-stack/build/dpdk-build` и поставит его первым, даже если `PKG_CONFIG_PATH` уже задан;
   какой `libdpdk.pc` взят — печатает. В `DPERF_DIR` должен лежать Makefile dperf (исходники).
3. **`env.sh`** — заполнить и положить одинаковым на обе машины:
   - `*_PCI0` / `*_PCI1` — порты mlx5 с доменом: `lspci -D | grep -i mellanox`;
   - `*_CPUS` — до 12 ядер на NUMA-узле карты: `cat /sys/bus/pci/devices/<pci>/numa_node`, `lscpu`;
   - адреса можно оставить как есть: стенд — изолированная L2-сеть между двумя машинами;
   - `CLIENT_MAC` / `SERVER_MAC` — MAC портов PCI0 (их печатает `host_tune.sh`). Необязательно,
     но тогда dperf не ждёт ARP от соседа и порядок запуска не важен (см. «Запуск»).
4. **После каждой перезагрузки**: `sudo ./host_tune.sh server` на B и `sudo ./host_tune.sh client` на A.
   Скрипт выделяет 8 ГБ hugepages по 1 ГБ на NUMA-узле карты, ставит governor performance,
   уводит прерывания с DPDK-ядер, поднимает ядерные интерфейсы тестовых портов и снимает с них IP.
   Если 1 ГБ-страницы не выделились (фрагментация памяти), добавьте в grub
   `hugepagesz=1G hugepages=<узел>:8`.

mlx5 работает через bifurcated-драйвер: ничего перепривязывать не нужно. Но ядерные интерфейсы
тестовых портов должны быть подняты, без IP и не входить в Linux bond — за это отвечает `host_tune.sh`.

## Запуск

```
машина B:  ./s1_dperf.sh server
машина A:  ./s1_dperf.sh client
```

Шаг — это подсценарий: `bond0-vxlan0`, `bond0-vxlan1`, `bond1-vxlan0`, `bond1-vxlan1`. На каждом шаге:

1. **B, Enter** — сервер поднимается с max(`S1_CORES`) воркерами. Статистику он начнёт печатать, когда узнает
   MAC клиента. Если `CLIENT_MAC` не задан, это произойдёт по ARP после старта клиента, так что запустите клиента
   в течение минуты. С заданными `CLIENT_MAC` и `SERVER_MAC` ограничения нет: сервер сразу пишет `[srv ...] 0s rx ...`.
2. **A, Enter** — клиент сам перебирает число воркеров N из `S1_CORES` (1 2 3 4 6 8 10 12).
   Каждая точка идёт около минуты: 10 с разгон, 30 с замер, 4 с останов, плюс запуск DPDK.
   После точки печатается строка-итог, после шага — таблица.
3. Когда клиент закончил шаг: **B, Enter** — остановить этот шаг и запустить следующий. Потом снова **A, Enter**.

Весь сценарий занимает около 35 минут. На сервере 5 нажатий Enter: запуск и по одному после каждого шага,
на клиенте 4 — по одному на шаг.

Отдельный шаг или свой набор точек — переменными, **одинаково на обеих машинах**:

```
S1_BOND=1 S1_VXLAN=0 ./s1_dperf.sh server
S1_BOND=1 S1_VXLAN=0 S1_CORES="2 4 6" ./s1_dperf.sh client   # макс. N клиента ≤ макс. N сервера
```

Логи лежат в `results/s1-<дата>-<роль>/bond<B>-vxlan<V>/`: у клиента `nNN.conf` и `nNN.log` на каждую
точку, у сервера `server.conf` и `server.log` на шаг. Каждая строка лога начинается с Unix-времени —
по нему клиент и сервер сводятся в одной таблице.

## Анализ

Клиент печатает таблицы сам: после каждого шага и в конце. Чтобы добавить загрузку CPU сервера,
скопируйте каталог сервера на машину клиента (часы машин должны быть синхронизированы через NTP):

```
scp -r B:<...>/perf-tests/results/s1-<дата>-server results/
./parse_dperf.py results/s1-<дата>-client results/s1-<дата>-server [--csv s1.csv]
```

```
== s1-20261006-120000-client / bond0-vxlan0
 cores  Gbps_rx  Gbps_tx  Gbps_sum    Mpps  Gbps/core  cpu_cli  cpu_srv   drops   retr
     1     71.3     71.3     142.6    11.8      142.6      99%      97%       0      0
     2    140.1    140.1     280.2    23.1      140.1      99%      96%       0      0
     3    194.0    194.0     388.0    32.0      129.3      91%      88%       0      0  <- оптимум
     4    196.9    196.9     393.8    32.5       98.5      69%      66%       0      0
максимум 393.8 Gbps при N=4; оптимум N=3: 388.0 Gbps (99% от максимума, 129.3 Gbps на ядро)
```

(Цифры условные — это пример формата, а не прогноз.)

- **Gbps_rx / Gbps_tx / Gbps_sum** — средние за окно замера. В окно идут секунды `[--skip 15, последняя − --tail 5]`:
  без разгона и останова. dperf считает байты L2-кадра без FCS, преамбулы и межкадрового промежутка,
  поэтому потолок одного 200G-порта на кадрах 1514 Б — **196.9 Gbps в каждую сторону** (200 × 1514 / 1538).
- **Mpps** — пакеты rx + tx в секунду.
- **cpu_cli / cpu_srv** — cpuUsage из dperf, средний по N активным воркерам. Ядро DPDK всегда занято опросом
  на 100%, а cpuUsage — это доля циклов, в которых воркер реально обрабатывал пакеты.
  Если на оптимуме он заметно ниже 100%, узкое место — канал или PCIe, а не CPU.
- **drops** — dropTx, tcpDrop, badRx и прирост ierrors/oerrors/imissed за окно (клиент + сервер).
  **retr** — ретрансмиты и skErr. В норме оба равны 0.
- **оптимум** — минимальное N, дающее ≥ 95% от максимума шага (`--opt 0.9` меняет порог).
- В конце — сводная таблица по шагам. `--csv` выгружает все точки. `--brief` — одна строка на лог.

Парсер понимает любой вывод dperf: перехваченный stdout или `/var/log/dperf/*.log` при `daemon`.
В daemon-лог dperf дописывает прогоны подряд, парсер берёт последний. Для чужих логов подберите
`--skip` и `--tail` под их `slow_start` и `duration`.

Про bond: двухпортовая карта на PCIe Gen4 x16 вместе отдаёт около 200–220 Gbps в каждую сторону,
так что 2×200G в bond упрётся в шину. Полные 2×200G возможны на двух картах или на PCIe Gen5 x16 (ConnectX-7).

## Что настроено для максимума и почему

- **Кадры полного размера.** payload 1460 даёт кадр 1514 Б. С VXLAN payload 1410: внешние заголовки
  добавляют 50 Б, и внешний кадр снова 1514 Б. Сам dperf VXLAN в проверке размера не учитывает и пропустит
  1460 — тогда кадр будет 1564 Б, больше MTU.
- **Замкнутый цикл без потерь.** `keepalive 0us` и `cc` = 2000 на воркер: следующий запрос уходит сразу
  после ответа. В полёте не больше cc пакетов на воркер, а это меньше RX-кольца dperf (4096),
  поэтому кольца не переполняются. Пропускная упирается в CPU или канал, а не в параметры нагрузки.
  Чистых ACK нет: подтверждение уходит вместе со следующим запросом. На каждую транзакцию —
  два полноразмерных кадра, по одному в каждую сторону.
- **`tx_burst 128`** вместо 8 по умолчанию. Больше 255 ставить нельзя: в dperf это поле `uint8`,
  и, например, 1024 молча превращается в 8.
- **FDIR 1:1.** На каждый воркер свой IP сервера (с VXLAN — свой VTEP). Воркер i клиента работает
  с воркером i сервера, без программного переноса сокетов между воркерами, как в режиме `rss`.
  VXLAN в dperf иначе и не работает: RSS для VXLAN не поддерживается.
- **Сервер с max(N) воркерами на шаг.** При N клиентских воркерах нагружены ровно N серверных,
  остальные простаивают. Каждая точка — честные N:N, и сервер не надо перезапускать на каждую точку.
- **bond 802.3ad, хеш L3+L4** (`bond4:2(...)`). Соединения расходятся по обоим линкам по портам клиента.
  Первые секунды, пока сходится LACP, приходятся на разгон и в замер не попадают.
- **Хост.** Ядра изолированы и стоят на NUMA-узле карты, hugepages на том же узле,
  governor performance, прерывания вне DPDK-ядер, `iommu=pt`.
- **`JUMBO=1`** — по желанию, на обеих машинах: MTU 9000, payload 8960 (с VXLAN 8910), примерно в 6 раз
  меньше пакетов на тот же объём. Пул dperf — 64K jumbo-mbuf по 11 КБ, около 0.75 ГБ на очередь.
  При 8 ГБ hugepages это не больше 10 воркеров: `JUMBO=1 S1_CORES="1 2 4 6 8 10"`.

## Если что-то не так

- **`Error: bad gateway`** — dperf 60 с не получил ARP-ответа от соседа. Запустите вторую сторону раньше
  или пропишите `CLIENT_MAC` / `SERVER_MAC` в `env.sh`. Проверьте линк: `host_tune.sh` печатает скорость портов.
- **`socket allocation failed`, `rte_pkt_pool_create error`** — мало hugepages на NUMA-узле карты:
  `grep -i huge /proc/meminfo`, затем повторить `host_tune.sh`.
- **`Error: Interface dose not support FDIR`** — не создалось правило rte_flow. Пришлите лог: для шагов
  без VXLAN можно перейти на режим `rss`.
- **`PCI ... не найден`** — проверьте адреса в `env.sh`: полный вид `0000:3b:00.0`.
- **drops / retr ≠ 0** — потери. Смотрите imissed (не успевает RX: обычно ядро не на том NUMA-узле
  или не изолировано) и dropTx (переполнено TX-кольцо).
- **Ctrl-C** на клиенте прерывает сценарий. На сервере Ctrl-C корректно останавливает dperf.
