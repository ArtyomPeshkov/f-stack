# Стенд производительности: dperf ↔ dperf и dperf → nginx

Две машины, прямое соединение, mlx5 200GbE. Машина A — dperf client, машина B — сервер.

- **Сценарий 1** — dperf ↔ dperf, на машине B dperf server. Перебираются 4 подсценария:
  bond / без bond × VXLAN / без VXLAN. В каждом ищутся максимальная пропускная способность
  и минимальное число ядер, на котором она достигается.
- **Сценарий 2** — dperf → nginx, на машине B nginx на ядерном стеке и на F-Stack. Пока без bond
  и VXLAN. Сравниваются пропускная способность и загрузка CPU при одинаковом числе ядер,
  см. [раздел ниже](#сценарий-2-dperf--nginx-на-ядре-и-на-f-stack).

| файл | назначение |
|---|---|
| `env.sh` | все параметры стенда: PCI, IP, ядра, план. Один и тот же файл на обеих машинах |
| `build_dperf.sh` | собирает dperf статически на DPDK из f-stack (`f-stack/build/dpdk-build`) |
| `host_tune.sh` | подготовка машины после перезагрузки: hugepages, governor, IRQ, интерфейсы mlx5 |
| `s1_dperf.sh` | сценарий 1: `server` на машине B, `client` на машине A |
| `s2_nginx.sh` | сценарий 2: `server` на машине B, `client` на машине A |
| `nginx/` | шаблоны конфигов сценария 2: nginx на ядре, nginx на F-Stack, f-stack.conf |
| `common.sh` | общее для s1 и s2: запуск dperf с метками времени, вывод в терминал |
| `parse_dperf.py` | парсер логов dperf: таблицы, оптимум по ядрам, kernel против F-Stack, CSV |

Ожидаемая раскладка (как у вас):

```
<каталог>/f-stack/perf-tests/      эти файлы
<каталог>/f-stack/build/dpdk-build собранный DPDK (meson build-каталог или install-prefix)
<каталог>/dperf/                   исходники dperf (проверено на v1.9.0)
```

Пути переопределяются переменными `FSTACK_DIR`, `DPDK_BUILD`, `DPERF_DIR`, `DPERF`, `RESULTS`.

## Сценарий 1: dperf ↔ dperf

### Подготовка (один раз)

1. **BIOS и параметры ядра** на обеих машинах:
   - BIOS: профиль Performance, C-states выключены, турбо — в одном и том же положении на обеих машинах;
   - grub: `iommu=pt` (`intel_iommu=on` или `amd_iommu=on`), изоляция DPDK-ядер
     `isolcpus=<ядра> nohz_full=<ядра> rcu_nocbs=<ядра>`, затем перезагрузка;
   - HT: в списки ядер `env.sh` берите по одному потоку на физическое ядро.
2. **Сборка dperf** на обеих машинах: `./build_dperf.sh`. Скрипт сам найдёт `libdpdk.pc`
   в `f-stack/build/dpdk-build` и поставит его первым, даже если `PKG_CONFIG_PATH` уже задан;
   какой `libdpdk.pc` взят — печатает. В `DPERF_DIR` должен лежать Makefile dperf (исходники).
3. **`env.sh`** — заполнить и положить одинаковым на обе машины:
   - `*_PCI0` / `*_PCI1` — порты mlx5 с доменом: `lspci -D | grep -i mellanox`;
   - `*_CPUS` — до 12 ядер на NUMA-узле карты: `cat /sys/bus/pci/devices/<pci>/numa_node`, `lscpu`;
   - адреса можно оставить как есть: стенд — изолированная L2-сеть между двумя машинами;
   - `CLIENT_MAC` / `SERVER_MAC` — MAC портов PCI0 (их печатает `host_tune.sh`). Необязательно,
     но тогда dperf не ждёт ARP от соседа и порядок запуска не важен (см. «Запуск»).
4. **После каждой перезагрузки**: `sudo ./host_tune.sh server` на B и `sudo ./host_tune.sh client` на A.
   Скрипт выделяет `HUGEPAGES_GB` hugepages на NUMA-узле карты, ставит governor performance,
   уводит прерывания с DPDK-ядер, поднимает ядерные интерфейсы тестовых портов, снимает с них IP
   и печатает их MAC. Сначала он пробует страницы по 1 ГБ. На работающей системе их часто не набрать:
   память фрагментирована. Тогда скрипт берёт страницы по 2 МБ — на скорость dperf это почти не влияет.
   Страницы по 1 ГБ гарантированно даёт только параметр загрузки
   `default_hugepagesz=1G hugepagesz=1G hugepages=8`. dperf без jumbo на 12 воркеров хватает 4 ГБ.

mlx5 работает через bifurcated-драйвер: ничего перепривязывать не нужно. Но ядерные интерфейсы
тестовых портов должны быть подняты, без IP и не входить в Linux bond — за это отвечает `host_tune.sh`.

### Запуск

```
машина B:  ./s1_dperf.sh server
машина A:  ./s1_dperf.sh client
```

Шаг — это подсценарий: `bond0-vxlan0`, `bond0-vxlan1`, `bond1-vxlan0`, `bond1-vxlan1`. Внутри шага обе стороны
перебирают число воркеров N из `S1_CORES` (1 2 3 4 6 8 10 12), на каждой точке у клиента и сервера ровно по N
воркеров. На каждом шаге:

1. **B, Enter** — сервер поднимается с первым N. Статистику он начнёт печатать, когда узнает MAC клиента.
   Если `CLIENT_MAC` не задан, это произойдёт по ARP после старта клиента, так что запустите клиента в течение
   минуты. С заданными `CLIENT_MAC` и `SERVER_MAC` ограничения нет.
2. **A, Enter** — клиент проходит все точки подряд. Каждая точка: 10 с разгон, 30 с замер, 4 с останов,
   запуск DPDK и пауза `S1_PAUSE` (20 с). После точки печатается строка-итог, после шага — таблица.
3. Сервер сам следит за трафиком: когда прогон клиента закончился (трафик ниже 1 Gbps 3 секунды подряд),
   он перезапускается со следующим N, а после последней точки предлагает следующий шаг.
   Если от клиента 5 минут нет трафика, сервер переходит к следующей точке сам.

Нажатий — по одному Enter на шаг на каждой машине, сначала на сервере. Весь сценарий — около 45 минут.

Отдельный шаг или свой набор точек — переменными, **одинаково на обеих машинах** (порядок точек должен совпадать):

```
S1_BOND=1 S1_VXLAN=0 S1_CORES="2 4 6" ./s1_dperf.sh server
S1_BOND=1 S1_VXLAN=0 S1_CORES="2 4 6" ./s1_dperf.sh client
```

Логи лежат в `results/s1-<дата>-<роль>/bond<B>-vxlan<V>/`: `nNN.conf` и `nNN.log` на каждую точку, на обеих
машинах. Каждая строка лога начинается с Unix-времени — по нему клиент и сервер сводятся в одной таблице.

### Анализ

Клиент печатает таблицы сам: после каждого шага и в конце. Чтобы добавить загрузку CPU сервера,
скопируйте каталог сервера на машину клиента (часы машин должны быть синхронизированы через NTP):

```
scp -r B:<...>/perf-tests/results/s1-<дата>-server results/
./parse_dperf.py results/s1-<дата>-client results/s1-<дата>-server [--csv s1.csv]
```

```
== s1-20261006-120000-client / bond0-vxlan0
 cores  Gbps_rx  Gbps_tx  Gbps_sum    Mpps  Gbps/core  cpu_cli  cpu_srv   drops   retr
     1     71.3     71.3     142.6    11.8      142.6      99%      97%       0      0
     2    140.1    140.1     280.2    23.1      140.1      99%      96%       0      0
     3    194.0    194.0     388.0    32.0      129.3      91%      88%       0      0  <- оптимум
     4    196.9    196.9     393.8    32.5       98.5      69%      66%       0      0
максимум 393.8 Gbps при N=4; оптимум N=3: 388.0 Gbps (99% от максимума, 129.3 Gbps на ядро)
```

(Цифры условные — это пример формата, а не прогноз.)

- **Gbps_rx / Gbps_tx / Gbps_sum** — средние за окно замера. В окно идут секунды `[--skip 15, последняя − --tail 5]`:
  без разгона и останова. dperf считает байты L2-кадра без FCS, преамбулы и межкадрового промежутка,
  поэтому потолок одного 200G-порта на кадрах 1514 Б — **196.9 Gbps в каждую сторону** (200 × 1514 / 1538),
  то есть 393.8 Gbps в Gbps_sum.
- **Mpps** — пакеты rx + tx в секунду.
- **cpu_cli / cpu_srv** — cpuUsage из dperf, средний по N активным воркерам. Ядро DPDK всегда занято опросом
  на 100%, а cpuUsage — это доля циклов, в которых воркер реально обрабатывал пакеты.
  Если на оптимуме он заметно ниже 100%, узкое место — канал или PCIe, а не CPU.
- **drops** — dropTx, tcpDrop, badRx и прирост ierrors/oerrors/imissed за окно (клиент + сервер).
  **retr** — ретрансмиты и skErr. В норме оба равны 0.
- **оптимум** — минимальное N, дающее ≥ 95% от максимума шага (`--opt 0.9` меняет порог).
- В конце — сводная таблица по шагам. `--csv` выгружает все точки. `--brief` — одна строка на лог.

Парсер понимает любой вывод dperf: перехваченный stdout или `/var/log/dperf/*.log` при `daemon`.
В daemon-лог dperf дописывает прогоны подряд, парсер берёт последний. Для чужих логов подберите
`--skip` и `--tail` под их `slow_start` и `duration`.

Про bond: двухпортовая карта на PCIe Gen4 x16 вместе отдаёт около 200–220 Gbps в каждую сторону,
так что 2×200G в bond упрётся в шину. Полные 2×200G возможны на двух картах или на PCIe Gen5 x16 (ConnectX-7).

### Что настроено для максимума и почему

- **Кадры полного размера.** payload 1460 даёт кадр 1514 Б. С VXLAN payload 1410: внешние заголовки
  добавляют 50 Б, и внешний кадр снова 1514 Б. Сам dperf VXLAN в проверке размера не учитывает и пропустит
  1460 — тогда кадр будет 1564 Б, больше MTU.
- **Замкнутый цикл без потерь.** `keepalive 0us` и `cc` = 2000 на воркер: следующий запрос уходит сразу
  после ответа. В полёте не больше cc пакетов на воркер, а это меньше RX-кольца dperf (4096),
  поэтому кольца не переполняются. Пропускная упирается в CPU или канал, а не в параметры нагрузки.
  Чистых ACK нет: подтверждение уходит вместе со следующим запросом. На каждую транзакцию —
  два полноразмерных кадра, по одному в каждую сторону.
- **`tx_burst 128`** вместо 8 по умолчанию. Больше 255 ставить нельзя: в dperf это поле `uint8`,
  и, например, 1024 молча превращается в 8.
- **FDIR 1:1.** На каждый воркер свой IP сервера (с VXLAN — свой VTEP). Воркер i клиента работает
  с воркером i сервера, без программного переноса сокетов между воркерами, как в режиме `rss`.
  VXLAN в dperf иначе и не работает: RSS для VXLAN не поддерживается.
- **Сервер ровно с N воркерами на каждой точке.** Простаивающий воркер dperf всё равно на 100% крутит опрос карты
  и отнимает ядро у активных: соседний HT-поток, планировщик хоста, общий тепловой и энергобюджет процессора.
  На ВМ это стоило вдвое: с одним рабочим и 11 простаивающими воркерами сервер давал 48–60 Gbps
  в каждую сторону, с одним воркером — 97.
- **bond 802.3ad, хеш L3+L4** (`bond4:2(...)`). Соединения расходятся по обоим линкам по портам клиента.
  Первые секунды, пока сходится LACP, приходятся на разгон и в замер не попадают.
- **Хост.** Ядра изолированы и стоят на NUMA-узле карты, hugepages на том же узле,
  governor performance, прерывания вне DPDK-ядер, `iommu=pt`.
- **`JUMBO=1`** — по желанию, на обеих машинах: MTU 9000, payload 8960 (с VXLAN 8910), примерно в 6 раз
  меньше пакетов на тот же объём. Пул dperf — 64K jumbo-mbuf по 11 КБ, около 0.75 ГБ на очередь.
  При 8 ГБ hugepages это не больше 10 воркеров: `JUMBO=1 S1_CORES="1 2 4 6 8 10"`.

### Если что-то не так

- **`Error: bad gateway`** — dperf 60 с не получил ARP-ответа от соседа. Запустите вторую сторону раньше
  или пропишите `CLIENT_MAC` / `SERVER_MAC` в `env.sh`. Проверьте линк: `host_tune.sh` печатает скорость портов.
- **`socket allocation failed`, `rte_pkt_pool_create error`** — мало hugepages на NUMA-узле карты:
  `grep -i huge /proc/meminfo`, затем повторить `host_tune.sh`.
- **`Error: Interface dose not support FDIR`** — не создалось правило rte_flow. Пришлите лог: для шагов
  без VXLAN можно перейти на режим `rss`.
- **`PCI ... не найден`** — проверьте адреса в `env.sh`: полный вид `0000:3b:00.0`.
- **drops / retr ≠ 0** — потери. Смотрите imissed (не успевает RX: обычно ядро не на том NUMA-узле
  или не изолировано) и dropTx (переполнено TX-кольцо).
- **Ctrl-C** на клиенте прерывает сценарий. На сервере Ctrl-C корректно останавливает dperf.

## Сценарий 2: dperf → nginx на ядре и на F-Stack

Машина A — тот же dperf client, машина B — nginx 1.28 в двух сборках: на ядерном стеке и на F-Stack.
Bond и VXLAN пока не используются, работают только порты `*_PCI0`. Шаг — стек nginx: `kernel`, `fstack`.
Внутри шага перебираются число воркеров nginx N (`S2_CORES`: 1 2 4 6 8 12) и размер ответа
(`S2_SIZES`: 1k, 64k, 1m). Для каждого стека и размера ищутся максимум и минимальное N, на котором
он достигается. В конце строится сравнение kernel и F-Stack при одинаковом N.

Как устроено:
- **Ответы.** nginx отдаёт статические файлы `/n<N>/<размер>` из `results/s2-...-server/www`.
  N в пути — самопроверка: если сервер и клиент разошлись по точкам, nginx отвечает 404,
  и клиент видит это в httpErr.
- **Клиент.** dperf работает HTTP-клиентом в замкнутом цикле keepalive: следующий запрос уходит сразу
  после ответа. `cc` соединений из `S2_SIZES` — на всех воркерах вместе. Воркеров dperf
  `S2_CLIENT_CORES` (4), и у nginx столько же адресов: `SERVER_IP`, `SERVER_IP+1`, ...
  Воркер i ходит на свой адрес (FDIR, как в сценарии 1), поэтому ответы приходят прямо в его очередь.
- **Равные условия.** У nginx ровно N воркеров на первых N ядрах `SERVER_CPUS`.
  - Ядерный стек: у порта N каналов, их прерывания и XPS на тех же N ядрах. Вся сетевая работа ядра
    идёт там же, где nginx.
  - F-Stack: `lcore_mask` из тех же N ядер, воркер k nginx работает на k-м ядре маски.
- **Синхронизация.** Сервер перезапускает nginx на каждое N. Прогоны клиента он отсчитывает
  по счётчикам vport порта (`ethtool -S`: `rx/tx_vport_unicast_*`). Их ведёт карта, поэтому
  в них виден и трафик ядра, и трафик F-Stack, который DPDK забирает мимо ядра.

### Подготовка

На машине A — то же, что для сценария 1: собранный dperf и `host_tune.sh client`.

На машине B:

1. **Две сборки nginx 1.28** из `f-stack/app/nginx-1.28.0`. `FF_PATH` и `PKG_CONFIG_PATH` — те же,
   что при сборке lib F-Stack:
   ```
   cd f-stack/app/nginx-1.28.0
   ./configure --prefix=/usr/local/nginx_fstack --with-ff_module --with-cc-opt=-DNGX_CONF_BUFFER=131072
   make && make install
   ./configure --prefix=/usr/local/nginx --with-cc-opt=-DNGX_CONF_BUFFER=131072
   make && make install
   ```
   nginx из дерева F-Stack и без `--with-ff_module` линкуется с libfstack и DPDK, но работает на ядерном
   стеке, а версия и код у обеих сборок общие. Подойдёт и обычный nginx 1.28.0 с nginx.org.
   Пути к бинарникам задаются в `env.sh`: `NGINX_KERNEL`, `NGINX_FSTACK`.

   `-DNGX_CONF_BUFFER=131072` нужен только для `S2_BODY=return` с ответами больше 4 КБ: это размер буфера,
   которым nginx разбирает конфиг, и самый длинный параметр в нём (по умолчанию 4096). В этой ветке он
   задаётся при сборке (`src/core/ngx_conf_file.c`). Обычному nginx с nginx.org так его не передать:
   там понадобится такая же правка исходника.

   Если сборка с F-Stack падает на `undefined reference to 'ff_mbuf_set_timestamp'`, это ошибка текущего
   F-Stack: символ не экспортирован из libfstack. В этой ветке она исправлена в `lib/ff_api.symlist`.
   В своей копии добавьте в `lib/ff_api.symlist` строку `ff_mbuf_set_timestamp` после
   `ff_mbuf_set_vlan_info` и пересоберите lib.
2. **ff_top** — им замеряется загрузка CPU у F-Stack. Собирается командой `make -C f-stack/tools` с тем же
   `PKG_CONFIG_PATH`, что и lib, и попадает в `f-stack/tools/sbin/top` (`FF_TOP`). Без него F-Stack
   прогоняется, но колонка cpu_srv остаётся пустой.
3. **`sudo ./host_tune.sh server` после перезагрузки**, как в сценарии 1: hugepages для F-Stack,
   governor, прерывания, ядерный интерфейс порта поднят и без адресов.
4. **Порт 80 свободен.** Другого nginx на машине быть не должно. Если загружен `nf_conntrack` (docker,
   firewalld), ядерный стек тратит CPU на учёт соединений. Для чистого сравнения его лучше выгрузить,
   скрипт об этом предупредит.

Что `s2_nginx.sh server` меняет на машине B:
- **шаг kernel:**
  - адреса `SERVER_IP` ... `SERVER_IP+S2_CLIENT_CORES-1` с маской /24 на ядерном интерфейсе порта;
  - `net.core.somaxconn` и `net.ipv4.tcp_max_syn_backlog` = 65535;
  - на каждом N: `ethtool -L <порт> combined N`, привязка прерываний `mlx5_comp*` порта и XPS к ядрам nginx;
- **оба шага:** при большом `cc` поднимает `fs.nr_open`, если лимит дескрипторов nginx в него не влезает;
- **шаг fstack:** снимает адреса с ядерного интерфейса, порт работает через DPDK (bifurcated mlx5);
- **в конце:** снимает адреса с интерфейса.

### f-stack.conf

Шаблон — `nginx/f-stack.conf`. На каждую точку скрипт подставляет в него:
- `[dpdk] lcore_mask` — первые N ядер `SERVER_CPUS`; воркер k nginx работает на k-м ядре маски;
- `[dpdk] allow` — PCI порта (`SERVER_PCI0`);
- `[port0] addr`, `netmask`, `broadcast`, `gateway` — `SERVER_IP`/24, шлюз — `CLIENT_IP`;
- `[port0] vip_addr` — `SERVER_IP+1`, ... — по адресу на воркер dperf.

Остальное — значения из `f-stack/config.ini`, их можно менять прямо в шаблоне. Рычаги, которые
стоит пробовать:
- `tso=1` — большие ответы режет на сегменты карта, а не стек: главное для 64k и 1m;
- `pkt_tx_delay` — F-Stack до 100 мкс копит пакеты в пачку. При малых ответах и малой нагрузке 0
  уменьшает задержку;
- `idle_sleep=0` — чистый опрос, без сна;
- `net.inet.tcp.sendspace`, `sendbuf_inc`, `sendbuf_max` — буфер отправки, важен для больших ответов.

Итоговый конфиг каждой точки лежит в её каталоге на сервере.

### Запуск

```
машина B:  sudo ./s2_nginx.sh server
машина A:  ./s2_nginx.sh client
```

На каждом шаге (kernel, fstack) нажмите Enter сначала на сервере, потом на клиенте. Сервер поднимает
nginx с первым N и раз в секунду печатает трафик порта и загрузку ядер nginx. Клиент проходит все
точки N × размер. Каждая точка занимает около 47 с (10 с разгон, 30 с замер, останов и запуск DPDK)
плюс пауза `S2_PAUSE` (20 с). Шаг длится около 20 минут, весь сценарий — около 40.

nginx на F-Stack поднимается дольше: DPDK инициализируется в каждом воркере, это около 10 с.
На шаге fstack дайте серверу 10–15 с, прежде чем нажимать Enter на клиенте. Если между точками сервер
не успевает перезапустить nginx, увеличьте `S2_PAUSE`.

Отдельный стек или свой набор точек задаётся переменными, **одинаково на обеих машинах**.
С одним стеком шаг один: Enter на сервере, затем на клиенте.

```
только ядро:     B: sudo S2_STACKS=kernel ./s2_nginx.sh server    A: S2_STACKS=kernel ./s2_nginx.sh client
только F-Stack:  B: sudo S2_STACKS=fstack ./s2_nginx.sh server    A: S2_STACKS=fstack ./s2_nginx.sh client
свои точки:      B: sudo S2_STACKS=fstack S2_CORES="1 2" S2_SIZES="64k:1000" ./s2_nginx.sh server
                 A: S2_STACKS=fstack S2_CORES="1 2" S2_SIZES="64k:1000" ./s2_nginx.sh client
```

С sudo переменные пишутся после `sudo`: в варианте `S2_STACKS=kernel sudo ./s2_nginx.sh` sudo их
не передаст. Под root sudo не нужен.

Где лежат логи:
- клиент: `results/s2-<дата>-client/<стек>/nNN-<размер>.conf` и `.log`;
- сервер: `results/s2-<дата>-server/<стек>/nNN.log` — загрузка ядер nginx раз в секунду;
- сервер: каталог точки `nNN/` — `nginx.conf`, `return.conf`, `f-stack.conf`, `stdout.txt` (вывод nginx
  и F-Stack), `logs/error.log`, `fftop.txt` (вывод ff_top).

### Режимы: тело в конфиге, короткие соединения, много соединений

По умолчанию соединения живут весь прогон, а ответы — файлы (`S2_CONN=keepalive`, `S2_BODY=file`).
На больших ответах это проверка того, как стек перекладывает байты, и здесь впереди ядро с sendfile и TSO.
Выигрыш F-Stack стоит ждать там, где основная стоимость — системные вызовы, прерывания и установка
соединений: мелкие ответы и много новых соединений в секунду. Так мерили и разработчики F-Stack
(раздел «Nginx Testing Result» в README репозитория): тело 600 байт прямо из `nginx.conf`, короткие
соединения. Против ядра с `reuseport` F-Stack там быстрее в 1.4–2.3 раза на 8–16 ядрах, а на 1–4 ядрах
разница в пределах 1.2 раза.

- **`S2_BODY=return`** — ответ nginx отдаёт прямо из конфига директивой `return`, без открытия и чтения файла.
  Строка из конфига уходит в сокет без копирования внутри nginx, так что у обоих стеков остаются только их
  собственные копии.
  - Предел — самый длинный параметр конфига. Без пересборки это около 4000 байт, с nginx, собранным
    с `--with-cc-opt=-DNGX_CONF_BUFFER=131072` (см. «Подготовка»), — до 128 КБ, т. е. 16k и 64k влезают.
    Скрипт читает предел из `nginx -V` обоих nginx и берёт меньший, чтобы ядро и F-Stack отдавали из конфига
    одни и те же размеры. Ответы длиннее идут из файлов, об этом сервер пишет при старте.
  - `return` — директива модуля rewrite, он есть в обычной сборке; скрипт проверит.
- **`S2_CONN=close`** — короткие соединения, замер CPS. dperf держит `cc` соединений в полёте: каждое делает
  2 запроса, dperf закрывает его и сразу открывает новое. Новых соединений dperf открывает не больше
  `S2_CPS` (2 млн в секунду) — заведомо больше, чем выдержит nginx, так что упирается сервер.
  - Главная метрика — **Kcps**, тысяч новых соединений в секунду; Krps = 2 × Kcps.
  - Закрывает соединение клиент, поэтому TIME_WAIT не копится на сервере.
  - Такому потоку dperf нужно много сокетов. Адресов `CLIENT_IP`, `CLIENT_IP+1`, ... он берёт сколько нужно:
    при 4 воркерах и `S2_CPS` = 2 млн — 16. На адреса nginx они заходить не должны, скрипт это проверит.
- **Много одновременных соединений** — большой `cc` в `S2_SIZES`, например `600:300000`.
  - Лимиты nginx скрипт считает сам. `worker_connections` — наибольший `cc` в полтора раза больше
    (RSS делит соединения по воркерам неровно), делённый на число воркеров; дескрипторов — столько же.
    Если нужно, поднимает `fs.nr_open`. Адресов клиента dperf тоже добавит сам.
  - Без паузы между запросами при сотнях тысяч соединений ответ ждёт в очереди дольше таймаута
    ретрансмиссии dperf (2 с). Задайте паузу `S2_KEEPALIVE`, например `1s`. Тогда нагрузка —
    `cc` / `S2_KEEPALIVE` запросов в секунду, и при одинаковом трафике сравнивается загрузка CPU.
  - Память: nginx заранее выделяет около 450 байт на каждое место в `worker_connections` (1.5 млн мест —
    около 0.7 ГБ на воркер), ядро тратит несколько КБ на соединение. Начинайте с 200–300 тысяч.
  - Лимиты F-Stack не мешают: `maxfiles` он выводит из `physmem`, это десятки миллионов на процесс.

```
CPS, тело из конфига (как у разработчиков F-Stack):
  B: sudo S2_CONN=close S2_BODY=return S2_SIZES="600:4000" ./s2_nginx.sh server
  A: S2_CONN=close S2_BODY=return S2_SIZES="600:4000" ./s2_nginx.sh client
мелкие ответы на долгих соединениях:
  B: sudo S2_BODY=return S2_SIZES="600:2000 4000:2000" ./s2_nginx.sh server
  A: S2_BODY=return S2_SIZES="600:2000 4000:2000" ./s2_nginx.sh client
много одновременных соединений:
  B: sudo S2_BODY=return S2_SIZES="600:300000" S2_KEEPALIVE=1s ./s2_nginx.sh server
  A: S2_BODY=return S2_SIZES="600:300000" S2_KEEPALIVE=1s ./s2_nginx.sh client
```

Режим точки — `close-return`, `keepalive-return` и т. п. — пишется в логи и в заголовки таблиц.
kernel и F-Stack сравниваются только в одинаковом режиме.

### Анализ

Клиент печатает результаты сам: строку после каждой точки, таблицы после шага, в конце — итог
и сравнение. Чтобы добавить загрузку CPU nginx, скопируйте каталог сервера на машину клиента:

```
scp -r B:<...>/perf-tests/results/s2-<дата>-server results/
./parse_dperf.py results/s2-<дата>-client results/s2-<дата>-server [--csv s2.csv]
```

Если kernel и F-Stack запускались отдельно, передайте парсеру обе сессии клиента (и сервера):
сравнение строится по ним вместе, а если точка повторялась, берётся более поздний прогон.

```
./parse_dperf.py results/s2-<дата1>-client results/s2-<дата2>-client results/s2-<дата1>-server results/s2-<дата2>-server
```

```
== s2-20261006-100000-client / kernel / 64k
 cores     Gbps      Krps     Kcps  Gbps/core  cpu_srv  cpu_cli  httpErr   drops   retr
     1     31.6      60.0      0.0       31.6     100%      12%        0       0      0
     2     63.2     120.0      0.0       31.6     100%      21%        0       0      0
     4    126.3     240.0      0.0       31.6     100%      40%        0       0      0  <- оптимум
максимум 126.3 Gbps (240.0 Krps) при N=4; оптимум N=4: 126.3 Gbps (100% от максимума, 31.6 Gbps на ядро)

== kernel против F-Stack: s2-20261006-100000-client
  size cores kern_Gbps kern_Krps kern_Kcps kern_cpu  ff_Gbps  ff_Krps  ff_Kcps   ff_cpu  ff/kern
   64k     1      31.6      60.0       0.0     100%     78.9    150.0      0.0     100%    2.50x
   64k     4     126.3     240.0       0.0     100%    196.9    374.1      0.0      50%    1.56x
```

(Цифры условные — это пример формата, а не прогноз.)

- **Gbps** — ответы nginx, то есть rx клиента. Как и в сценарии 1, это L2 без FCS, потолок порта —
  196.9 Gbps.
- **Krps** — тысяч ответов 200 в секунду.
- **Kcps** — тысяч новых соединений в секунду. На долгих соединениях после разгона около 0,
  в режиме `S2_CONN=close` — главная метрика.
- **cpu_srv** — средняя загрузка N ядер nginx:
  - kernel: `/proc/stat`, user+system+irq+softirq. Прерывания порта на тех же ядрах, поэтому сюда входит
    и сетевой стек ядра;
  - fstack: ff_top, 100% − idle — доля цикла опроса, в которой F-Stack и nginx делали работу. Сам опрос
    держит ядро загруженным на 100% всегда.

  Около 100% — упор в CPU сервера. Заметно меньше при потолке Gbps — упор в порт, и тогда cpu_srv
  показывает, сколько CPU стеку нужно на ту же нагрузку.
- **cpu_cli** — cpuUsage dperf. Если он 90% и выше, упирается клиент. Увеличьте `S2_CLIENT_CORES`
  на обеих машинах: от него зависит и число адресов nginx.
- **httpErr** — ответы не 200. Если Krps равен 0, а httpErr растёт, nginx отвечает 404: сервер и клиент
  разошлись по точкам или нет файлов ответов. Такие точки в максимум и оптимум не идут, шаг нужно
  перезапустить на обеих машинах.
- **ff/kern** — во сколько раз F-Stack отвечает чаще ядра при том же N.

### Что настроено для максимума и почему

- **dperf.** HTTP-клиент с разбором ответов (Content-Length), замкнутый цикл `keepalive 0us`.
  dperf объявляет окно приёма около 478 МБ (wscale 13), так что скорость отправки ограничивают только
  nginx и его TCP.
- **nginx.** Без access_log, с `open_file_cache`, `keepalive_requests` 10^9: соединения живут весь
  прогон, ответы идут из page cache.
  - ядро: `sendfile` + `tcp_nopush`, `reuseport` (свой listen-сокет на воркер), epoll;
  - F-Stack: kqueue; sendfile на сокетах F-Stack нет, файл копируется через `output_buffers 2 256k`.
- **Ядерный стек.** N каналов порта, прерывание и XPS каждого канала — на ядре воркера, backlog 65535.
- **F-Stack.** TSO, чистый опрос.
- **`S2_KERNEL_SENDFILE=off`** — ядро без sendfile, как F-Stack. Так сравниваются именно стеки,
  без выигрыша ядра от zero-copy.

### Если что-то не так

- **Сервер остановился с «nginx не запустился» или «nginx завершился»** — смотрите `stdout.txt`
  и `logs/error.log` в каталоге точки. Там же вывод F-Stack: DPDK, hugepages, порт.
- **«dperf нужно N адресов ... заходят на адреса nginx»** — для такого `cc` или `S2_CPS` dperf нужно столько
  клиентских адресов, что они пересекаются с адресами nginx. Уменьшите `cc` или `S2_CPS` либо разнесите
  `CLIENT_IP` и `SERVER_IP` в `env.sh`.
- **«собран без модуля rewrite»** — для `S2_BODY=return` соберите nginx без `--without-http_rewrite_module`
  (модулю нужна PCRE), или запускайте с файлами (`S2_BODY=file`).
- **`Error: bad gateway` на клиенте** — nginx 60 с не отвечал на ARP: сервер не запущен,
  или F-Stack ещё поднимается.
- **Krps 0 и растёт httpErr** — см. «Анализ».
- **«5 минут без трафика от клиента» на сервере** — клиент не запустился. Сервер переходит
  к следующему N, сценарий надо перезапустить на обеих машинах.
- **Пустой cpu_srv у fstack** — нет ff_top, или он не подключился к F-Stack. Смотрите `fftop.txt`
  в каталоге точки.
